# 四阶段总路线

## 1. 项目目标

最终成果应满足两个标准：

1. 用户视角：系统可以完成可靠单聊、群聊、AI 工具调用、音视频通话和跨实例消息投递。
2. 面试视角：项目作者可以从需求、数据模型、请求链路、失败场景、技术取舍和改进方向六个角度解释每个功能。

## 2. 固定开发循环

每个功能都按以下顺序完成：

```text
需求场景
→ 接口/协议草图
→ 数据模型和约束
→ 最小实现
→ 单元测试/集成测试
→ 手工演示
→ 故障测试
→ 复盘与提交
```

禁止先铺满所有 Controller、Service、Repository 再统一实现。每次只完成一个可运行的垂直切片。

项目结构本身也是学习内容，必须手动完成：

- 不由 AI 创建目录树、`go.mod`、入口文件、配置文件或前端脚手架。
- 不提前创建后续 MVP 的空包。
- 每建立一个目录，都要能够说明它在 KamaChat 中对应什么职责。
- 使用 `go mod init`、Vue CLI/Vite 等命令前，先写下模块名和选择理由。
- 可以参考 KamaChat 的目录名称，但需要自己逐个创建和理解。

例如注册功能应一次贯通：

```text
POST /register
→ api/v1/user_info_controller.go
→ internal/service/gorm/user_info_service.go
→ MySQL
→ 统一响应
→ 测试
```

这条命名和分层优先贴近 KamaChat；可靠性、安全性改进在对应 MVP 文档中单独标记。

## 3. AI 使用边界

允许：

- 查询 API、标准库和第三方库文档。
- 让 Copilot 补全一个已经由你定义签名、输入输出和错误语义的函数。
- 请 AI 解释报错、比较两种方案、设计测试用例或进行代码审查。
- 请 AI 扮演面试官追问你的实现。

不允许：

- 让 AI 一次生成完整模块或整个 MVP。
- 在无法解释代码时直接接受补全。
- 把 KamaChat 的长函数整体复制到项目中。
- 为了使用技术栈而添加没有业务依据的组件。

Copilot 补全函数后的自检：

- 我能解释每一行吗？
- 我能写出至少一个失败测试吗？
- 我知道该函数的时间和空间复杂度吗？
- 我能指出它在并发、超时和异常输入下的行为吗？
- 关掉补全后，我能重新写出核心逻辑吗？

## 4. 每阶段交付物

每个 MVP 必须保存：

- 可运行版本和 Git Tag。
- 一张当前架构图。
- 至少一张核心时序图。
- 数据表和索引说明。
- HTTP/WebSocket/MCP 协议说明。
- 自动化测试结果。
- 一次故障注入记录。
- 一份“本阶段为什么要进入下一阶段”的复盘。
- 10 个项目追问及自己的口头答案。

建议 Tag：

```text
mvp0-core-chat
mvp1-group-redis
mvp2-ai-mcp
mvp3-realtime-distributed
```

## 5. 全局工程约束

- MySQL 是业务数据的事实来源。
- Redis 数据必须有过期或重建方案，不能成为唯一事实来源。
- WebSocket 身份来自服务端鉴权上下文，不能信任消息体中的 sender_id。
- 消息必须拥有服务端 ID；客户端重试必须有幂等依据。
- 同一 WebSocket 连接只能有一个写协程。
- 持锁期间不得进行网络写入或可能阻塞的 Channel 投递。
- 所有外部调用必须支持 context、超时和取消。
- 日志不得打印密码、Token、完整聊天隐私或模型密钥。
- API 使用真实 HTTP 状态码；业务错误不能统一伪装成 HTTP 200。
- 每个阶段先实现正确性，再用数据证明性能优化的必要性。
