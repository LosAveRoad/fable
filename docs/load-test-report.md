# Fable IM 压测与瓶颈定位报告

## 测试口径

压测从独立客户端发起，k6 在 Docker 中运行。为绕过本地 DNS 代理，容器内将
`api.fableim.lol` 强制映射到 VPS2 `38.147.170.246`，同时保留域名用于 TLS/SNI。
目标接口为只读 `/healthz`，该接口不访问 MySQL、Redis 或 Kafka，因此结果只代表
公网接入层、Nginx、NodePort 和 Go HTTP 监听能力。

## 已完成结果

| 目标 RPS | 实际 RPS | 请求数 | 错误率 | p95 | p99 | 丢弃迭代 |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 99.51 | 3,000 | 0% | 169 ms | 225 ms | 0 |
| 200 | 199.13 | 6,000 | 0% | 166 ms | 412 ms | 0 |
| 500 | 491.72 | 14,934 | 0.26% | 169 ms | 未单独输出 | 67 |

500 RPS 时出现连接拒绝，说明当前拐点首先发生在连接/接入层，而不是普通
HTTP 请求处理延迟。当前可按 200 RPS 作为保守稳定容量，500 RPS 作为待定位
压力点，不能把 500 RPS 当作生产承诺容量。

## 分层实验计划

1. **路径校验**：确认公网 DNS、证书、Nginx、NodePort 实际目标；记录客户端
   CPU、网卡和连接数，排除压测机瓶颈。
2. **VPS2 接入层**：在 100/200/500 RPS 各运行 30 秒，同时采集 Nginx error log、
   active connections、`ss -s`、`somaxconn`、文件描述符、CPU、内存和网卡。
3. **绕过 Nginx**：从 VPS2 本机访问 `127.0.0.1:30080`，对比 HTTPS 公网结果，
   判断 TLS/Nginx 是否为瓶颈。
4. **绕过 NodePort**：临时端口转发到 Pod 或直接访问 Pod，判断 kube-proxy/NodePort
   是否导致连接拒绝。
5. **业务 API**：使用专用测试账户测试登录、群列表、历史消息和发送消息；记录
   Go 延迟、MySQL 连接/慢查询、Redis 命中率、Kafka 吞吐和 consumer lag。
6. **WebSocket**：逐级测试 100/500/1000 长连接，随后测试消息发送和群广播，记录
   建连成功率、断线率、广播延迟和 Pod 内存。
7. **耐久性**：选定安全容量运行 30 分钟，确认没有内存泄漏、连接泄漏、Kafka lag
   累积或数据库连接池耗尽。

## 判定标准

- 稳定：错误率 < 1%，p95 < 500 ms，Pod 无重启，Kafka lag 不持续增长。
- 警戒：错误率 1%～5%、p95 超过 500 ms、连接数或资源持续增长。
- 上限：错误率 > 5%、出现连接拒绝/Pod 重启、数据库或 Kafka 不可用。
