# Fable Chat：Kafka 面试追问

## 简历描述

> 消息持久化一次后发布投递事件；各 Fable 实例使用独立稳定 consumer group，消费端仅执行本地 WebSocket fan-out，避免共享 group 漏投及多实例重复写库。

## 1. Kafka 在项目中的作用

### 问题

介绍一下项目中 Kafka 的使用。

### 回答

Fable 有两个应用实例，每个实例只管理连接在本机的 WebSocket。发送消息时，接收请求的实例先把消息持久化到 MySQL，再向 Kafka 发布投递事件。每个 Fable 实例使用独立 consumer group 消费同一事件，消费后只查找本机连接并投递，不再写数据库。

Kafka在这里解决跨实例事件传播，MySQL负责消息历史，进程内连接表负责本地 WebSocket 路由。

### 追问

为什么不用应用实例之间直接调用 HTTP 接口？

### 追问的回答

直接调用要求发送方知道目标用户位于哪个实例，还需要维护实例发现、失败重试和扩缩容后的路由信息。Kafka把发送方与具体接收实例解耦，发送方只发布事件，各实例独立消费并检查本机连接。

HTTP 调用适合同步请求响应；实时投递事件不要求发送方等待每个实例返回结果，更适合通过消息系统异步传播。

## 2. Consumer Group

### 问题

为什么每个 Fable 实例使用独立 consumer group？

### 回答

Kafka 在同一个 consumer group 内分配分区，一条消息只会被 group 中的一个消费者处理。Fable 需要每个实例都看到投递事件，才能判断目标用户是否连接在本机，因此每个实例使用独立 group，形成 fan-out。

实例 group 使用稳定 Pod 名组成，例如 `fable-chat-fable-0`，使滚动更新后仍能恢复原消费身份和 offset。

### 追问

如果两个实例共用一个 consumer group，会发生什么？

### 追问的回答

事件可能被 `fable-0` 消费，但目标用户连接在 `fable-1`。前者找不到本地连接，后者又没有收到事件，实时投递就会缺失。

共享 group 适合把任务分摊给任意一个消费者；Fable 的需求是所有实例都收到事件，两者消费语义不同。

## 3. Offset 与提交时机

### 问题

消费者处理消息后，offset 是什么时候提交的？

### 回答

项目使用 `FetchMessage` 拉取消息，完成 JSON 解析和本地投递处理后，再调用 `CommitMessages` 提交 offset。这样处理失败时不会提前确认消息。

新 consumer group 从最新 offset 开始，避免新扩容实例把历史投递事件重新推送给当前在线用户；已经持久化的历史消息由 MySQL 查询提供。

### 追问

先处理再提交能保证消息只处理一次吗？

### 追问的回答

不能。处理成功后、提交 offset 前如果进程崩溃，重启后可能再次消费同一消息，所以通常属于至少一次处理。消费端需要幂等，或者允许重复事件不产生错误结果。

Fable 消费端只做在线 WebSocket 通知，不重复写数据库；严格的消息去重还可以利用 event ID 记录短期消费状态。

## 4. 分区与顺序

### 问题

Kafka 如何保证消息顺序？

### 回答

Kafka只保证同一分区内的消息顺序，不保证不同分区之间的全局顺序。生产者通过消息 key 选择分区，相同 key 通常会落到同一分区，从而保持该业务维度内的顺序。

Fable 为群消息使用接收方或群 ID 作为 key，使同一会话的事件尽量进入同一分区；分区数同时决定一个 consumer group 的最大有效并行消费能力。

### 追问

增加 Kafka 分区数会有什么影响？

### 追问的回答

增加分区可以提高并行度，但已有 key 到分区的映射可能变化，扩分区前后的同一 key 不一定仍位于同一个分区，因此可能影响跨扩容时间点的顺序假设。

分区还会增加 broker 元数据、文件句柄和副本同步开销，所以不能只为了提高数字盲目增加。

## 5. 持久化与发布一致性

### 问题

消息写入 MySQL 后再发布 Kafka，如果发布失败怎么办？

### 回答

当前消息已经保存在 MySQL，接收方之后可以读取历史，但本次实时通知可能缺失。MySQL事务和 Kafka 发布分属两个系统，普通本地事务不能同时保证两者原子成功。

当前实现先保证消息历史，再尝试实时投递，没有宣称两套系统之间达到严格原子一致。

### 追问

如果要进一步保证可靠发布，你会怎么设计？

### 追问的回答

可以采用 transactional outbox：在同一个 MySQL 事务中写业务消息和 outbox 记录，后台发布器扫描未发送记录并写入 Kafka，成功后更新 outbox 状态。

这样数据库提交成功就一定留下待发布记录。发布器可能重复发送，因此事件需要唯一 ID，消费端仍应按至少一次语义设计幂等处理。

## 6. Kafka 独立八股

### 问题

Kafka 中 broker、topic、partition 和 replica 分别是什么？

### 回答

broker 是运行 Kafka 服务并保存数据的节点；topic 是消息的逻辑分类；partition 是 topic 的物理分片和并行单位；replica 是同一 partition 在不同 broker 上的副本。

每个 partition 有一个 leader，读写通常由 leader 处理，其他副本跟随同步。副本数必须结合 broker 数量，单 broker 无法提供跨节点副本容灾。

### 追问

ISR 是什么，`acks=all` 表示什么？

### 追问的回答

ISR 是与 leader 保持足够同步的一组副本。`acks=all` 要求 leader 等待当前 ISR 按配置完成确认后再向生产者返回成功，相比只等待 leader 本地写入具有更强持久性保证。

它仍受副本数和 `min.insync.replicas` 影响；如果只有一个 broker 和一个副本，`acks=all` 也不会凭空获得跨节点容灾能力。
