# Fable Chat：Redis 面试追问

## 简历描述

> 封装统一 key 与 JSON 缓存，为用户、联系人、会话、群信息及消息列表设置 TTL；写路径追加消息或失效关联 key，验证码校验成功后删除对应 key。

## 1. Redis 在项目中的作用

### 问题

介绍一下项目中 Redis 的使用。

### 回答

Redis 主要承担查询缓存和短期验证码存储。项目为用户信息、联系人列表、会话列表、群信息、群成员和消息列表设计统一 key 前缀，并通过 JSON 序列化封装通用的 Get、Set 和追加操作，缓存默认 TTL 为 10 分钟。

读取时先查 Redis，未命中再查 MySQL并回填；写入后根据数据关系追加消息缓存或删除受影响的列表和详情 key。

### 追问

为什么使用 Cache Aside，而不是每次都先写缓存？

### 追问的回答

Cache Aside 让 MySQL 作为数据事实来源，缓存只保存热点查询结果。读未命中时由应用加载数据库并回填，写操作先完成数据库变更，再删除或更新相关缓存。

这样缓存故障不会改变数据的最终归属，业务也不需要把所有数据预先装入 Redis。

## 2. 缓存一致性

### 问题

数据库更新后，项目怎么处理缓存一致性？

### 回答

列表或详情发生结构变化时，项目删除相关 key，让下一次读取重新从 MySQL加载；发送消息时，如果消息列表缓存已经存在，则追加规范化消息，同时删除受影响的会话列表缓存。

删除缓存比直接构造并覆盖复杂聚合结果更简单，因为下一次查询会基于数据库最新状态重建缓存。

### 追问

先更新数据库再删除缓存，是否仍可能读到旧数据？

### 追问的回答

可能。并发读可能在数据库提交前读取旧值，又在删除缓存后把旧值回填，形成短暂不一致。常见缓解方式包括合理 TTL、延迟双删、按 key 加互斥、通过 binlog/消息异步失效，以及让业务接受短时间最终一致。

具体方案要根据一致性要求选择；缓存不能替代数据库事务。

## 3. TTL

### 问题

为什么缓存要设置 TTL？

### 回答

TTL 可以限制陈旧数据长期存在，也能让不再访问的 key 自动回收，控制 Redis 内存占用。Fable 的查询缓存默认保留 10 分钟，写路径还会主动删除相关 key，因此 TTL 同时承担兜底失效作用。

TTL 不是越长越好：过长会增加陈旧窗口，过短会降低命中率并增加数据库压力。

### 追问

大量 key 同时过期会有什么问题？

### 追问的回答

大量热点 key 在同一时间失效，查询会集中回源数据库，形成缓存雪崩。可以在基础 TTL 上增加随机抖动，避免过期时间集中；还可以使用多级缓存、请求限流和预热热点数据。

如果是单个热点 key 失效导致大量请求同时回源，通常称为缓存击穿，可以用互斥重建或逻辑过期减少并发回源。

## 4. 验证码

### 问题

验证码为什么放在 Redis 中？

### 回答

验证码生命周期短，需要按手机号快速读写并自动过期，Redis 的 String 和 TTL 很适合这种临时状态。项目写入验证码时同时设置一分钟过期时间，校验成功后删除对应 key，避免正常流程中重复使用。

### 追问

当前“读取、比较、删除”是原子操作吗？

### 追问的回答

不是。当前实现先 GET，在应用中比较，再 DEL；两个并发请求可能同时读到相同验证码并都通过比较。要实现严格的一次性消费，可以使用 Lua 脚本在 Redis 内原子完成读取、比较和删除，或使用支持相应语义的原子命令组合。

因此简历只描述“校验成功后删除”，不把当前实现夸大为并发下严格的一次性消费。

## 5. Redis 独立八股：数据类型

### 问题

Redis 常用数据类型和场景有哪些？

### 回答

String 可存字符串、数字和序列化对象，常用于缓存、计数和验证码；Hash 适合对象字段；List 适合双端队列；Set 适合集合去重和关系判断；Sorted Set 根据 score 排序，常用于排行榜；Stream 适合带消费组的消息流。

选择类型应看访问模式，而不是只看数据外观。例如需要按分数范围查询时 Sorted Set 比把数组序列化成 String 更合适。

### 追问

Redis 为什么快？

### 追问的回答

核心数据主要在内存中，避免磁盘随机访问；Redis 命令处理模型减少了共享数据结构上的线程竞争；底层针对不同类型使用高效数据结构，并通过 IO 多路复用处理大量连接。

“单线程”主要指命令执行路径，现代 Redis 的网络读取、持久化等部分可以使用其他线程，不能简单说整个 Redis 进程只有一个线程。

## 6. Redis 独立八股：持久化

### 问题

Redis 的 RDB 和 AOF 有什么区别？

### 回答

RDB 按时间点生成数据快照，文件紧凑、恢复较快，但两次快照之间的最新数据可能丢失。AOF 记录写命令并在启动时重放，通常能提供更小的数据丢失窗口，但文件更大，恢复和重写成本也更高。

Redis 可以只使用其中一种，也可以组合使用。缓存场景还可以不持久化，具体取决于 Redis 数据能否从其他来源重建。

### 追问

Fable 的 Redis 数据是否必须依赖持久化恢复？

### 追问的回答

查询缓存可以从 MySQL 重建，不依赖 Redis 持久化保证正确性；尚未过期的验证码如果丢失，会影响当前验证流程，但不会损坏 MySQL 业务数据。

当前 Compose 开启 AOF，主要减少 Redis 重启后的缓存和短期状态丢失。MySQL仍然是消息、用户和会话数据的事实来源。
