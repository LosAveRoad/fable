# Fable Chat：MySQL 与 GORM 面试追问

## 简历描述

> 设计用户、联系人、会话、单聊与群聊数据模型；用事务组织建群、加群及审批的多表写入，并以 MySQL 集成测试验证核心链路。

## 1. 数据模型

### 问题

介绍一下项目中的 MySQL 和 GORM 使用。

### 回答

MySQL 是 Fable 的业务数据事实来源，保存用户、联系人申请、联系人关系、会话、单聊消息、群信息和群消息。DAO 层通过 GORM 初始化连接和迁移表结构，Service 层使用条件查询、关联查询和事务完成业务操作。

模型把用户关系、会话和消息分开，使联系人状态、会话列表和消息历史可以独立查询，群聊则复用联系人关系表示成员资格。

### 追问

为什么消息和会话要分表？

### 追问的回答

消息表保存完整历史，数据量持续增长；会话表保存用户与聊天对象之间的会话关系，用于快速生成会话列表。两者的生命周期和查询模式不同，分开后不需要每次通过扫描大量消息来判断用户有哪些会话。

发送消息后可以单独让会话缓存失效，同时把消息写入消息历史，职责更清晰。

## 2. 数据库事务

### 问题

项目中哪些操作使用了数据库事务？

### 回答

建群需要同时写群信息、群主的群联系人关系和群会话；加群和审批也可能同时更新申请状态、成员关系和会话。项目使用 `GormDB.Transaction` 把这些多表写入放在同一个事务中，任一步返回错误就回滚。

事务边界放在 Service 层，因为 Service 最清楚一次业务操作需要保持一致的多条数据库语句。

### 追问

事务具有什么 ACID 特性？

### 追问的回答

原子性表示事务内操作要么全部成功、要么全部回滚；一致性表示事务前后数据满足业务约束；隔离性控制并发事务之间能观察到什么；持久性表示提交后的数据在系统故障后仍应保留。

ACID 不是调用一个 Transaction API 就自动获得全部业务正确性，表约束、隔离级别、错误处理和存储引擎配置都参与最终效果。

## 3. 隔离级别与 MVCC

### 问题

MySQL 常见事务隔离级别有哪些？

### 回答

从弱到强包括 Read Uncommitted、Read Committed、Repeatable Read 和 Serializable。隔离越强，并发事务之间可见的数据越受限制，通常并发成本也越高。

InnoDB 默认使用 Repeatable Read，并通过 MVCC 与锁共同处理并发读取和写入。普通一致性读通常读取快照，当前读和写操作还会涉及记录锁或间隙相关锁。

### 追问

MVCC 大致是怎么实现的？

### 追问的回答

InnoDB 行记录包含事务相关隐藏信息，旧版本通过 undo log 形成版本链。事务根据 Read View 判断哪些版本对当前读取可见，从而让很多普通读不必阻塞写操作。

MVCC 主要服务于快照读；`SELECT ... FOR UPDATE`、UPDATE 和 DELETE 等当前读需要读取最新可用版本，并结合锁保证并发修改正确性。

## 4. 索引与查询优化

### 问题

MySQL 索引为什么通常使用 B+Tree？

### 回答

B+Tree 分支多、树高低，适合减少磁盘页访问；数据主要位于叶子节点，叶子节点有序连接，既支持等值查询，也适合范围扫描和排序。相比二叉树，它在大数据量下需要的层数更少。

InnoDB 主键索引叶子节点保存整行数据，普通二级索引叶子节点保存索引列和主键值；通过二级索引查询其他列时可能需要回表。

### 追问

联合索引为什么要遵守最左前缀原则？

### 追问的回答

联合索引按定义列顺序构建有序键。例如索引 `(user_id, status, created_at)` 首先按 `user_id` 排序，只有在前一列范围确定后，后续列的有序性才便于继续定位。

设计联合索引时要结合真实 WHERE、JOIN、ORDER BY 和区分度，并通过 EXPLAIN 观察访问类型、候选索引、实际选择索引和预估扫描行数。

## 5. GORM 使用

### 问题

使用 GORM 有什么好处和风险？

### 回答

GORM 提供模型映射、参数绑定、事务封装和常见查询 API，减少重复 SQL 和扫描代码，也便于在测试中组织数据访问。项目仍显式编写 Where、Join、Order 和 Transaction，不把 ORM 当作无需理解 SQL 的抽象。

风险包括生成 SQL 不直观、关联加载引发 N+1 查询、零值更新语义容易误解，以及自动迁移不适合替代严格的生产 schema 变更流程。

### 追问

什么是 N+1 查询，怎么发现和解决？

### 追问的回答

先查询 N 条主记录，再为每条记录各发一次关联查询，就会产生一次主查询加 N 次子查询。数据量增大后，数据库往返次数和延迟会快速上升。

可以开启 SQL 日志或链路追踪观察重复查询，通过 JOIN、批量 `WHERE id IN (...)` 或合理使用 Preload 合并访问；是否使用 JOIN 还要考虑重复行和结果集大小。

## 6. 连接池与排查

### 问题

Go 访问 MySQL 时为什么需要连接池？

### 回答

建立数据库连接包含 TCP、认证和会话初始化成本，不能每个请求都重新连接。Go 的 `database/sql` 维护可复用连接池，GORM 底层也使用它，可以设置最大打开连接数、最大空闲连接数、连接最大生命周期和空闲时间。

连接数过小会让请求等待，过大会同时压垮数据库，所以要结合数据库 `max_connections`、应用实例数和请求耗时设置。

### 追问

接口突然变慢时，怎样判断是不是 MySQL 问题？

### 追问的回答

先区分应用等待连接、SQL 执行慢还是网络慢：查看连接池等待指标、MySQL processlist、慢查询日志和服务端资源；对具体 SQL 使用 EXPLAIN 或 EXPLAIN ANALYZE 检查索引、扫描行数和执行阶段。

还要关联请求时间窗口，检查锁等待、事务是否过长、连接数是否耗尽，以及 VPS2 到 VPS1 的网络 RTT，不能只看到接口慢就直接增加索引。
